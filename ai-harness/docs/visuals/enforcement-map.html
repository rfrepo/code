Where a write actually gets stopped

Every checkpoint between the agent deciding to change a file and that change reaching main — what fires it, what it can refuse, and whether it is code or a polite request.

Why not a call graph or a folder tree. A call graph shows what invokes what — but four of these checkpoints are invoked by the client, not by your code, and two don't exist yet, so they'd have no node. A folder tree shows where files sit, not when they fire or what they refuse. Enforcement is neither topology nor layout: it's a sequence of checkpoints between intent and effect. So this is a gauntlet, annotated with authority.

Enforcement is dense at the file boundary and empty at the workflow boundary. Every mechanism that actually refuses something lives at the moment a file is touched. Everything about which job this is and what order it happens in is prose.

Which is exactly why scope-by-location is the right fix rather than a runner: it enforces the workflow boundary using the file boundary — the one place enforcement already works. You are not adding a new kind of control. You are pointing the control you already have at the thing that has none.

What still can't be enforced, and shouldn't be. A hook refuses actions it can see. It cannot judge whether the abstraction was earned, whether the test is meaningful, or whether stage 4 was done well. That is the gates' and the reviewer's job, and no amount of hook is a substitute. The prose layer isn't a failure — it's the part that was always going to be prose. The failure was prose sitting where code belonged.
