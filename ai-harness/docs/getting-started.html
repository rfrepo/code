quality-harness getting started

Claude Code · Codex · humans · CI

Get the Quality Enforcement Harness running in a project

Layered, token-efficient quality gates for React/TS projects. One rulebook (docs/clean-code.md), enforced at the cheapest layer that can catch each violation — deterministic hooks first, AI judgement last.

What you get

A single gate script with three entry points (Claude hooks, git pre-commit, CI), write-time filename/protected-dir checks, format-and-lint on every edit, a turn-end Stop hook that chains gate → peer-review proof → LLM review, and an observability trail under .harness/runs/.

The layers

Deterministic rules  → hooks + ESLint (fire every time, zero tokens)
Soft design guidance → lean CLAUDE.md distillation (~15 lines, always on)
Procedures/reference → skills (loaded only when the task matches)
Judgment calls       → read-only reviewer subagent + pluggable AI reviewers
Turn-end enforcement → Stop hook: gate → peer-review proof → LLM review
Observability        → .harness/runs/: artifact bundles + JSONL activity feed
One source of truth  → docs/clean-code.md

Install

  1. Run the installer from your project root

    No argument needed — it installs into the directory you run it from:

    cd /path/to/project
bash /path/to/harness/install.sh

# or via npx from a local checkout:
npx --yes -p /path/to/harness quality-harness

# or once the harness is pushed to GitHub:
npx --yes github:<your-username>/quality-enforcement-harness

    It refuses to run outside a git repo root with a package.json. Everything it touches is backed up first; merges never clobber your config.

  2. Answer the prompts

    Protected dirs (Open-Closed enforcement), dev dependencies, optional extras (fallow, sonarjs, Stryker, TDD Guard), git hooks and CI workflows. Say no to anything — every piece works independently.

  3. Wire ESLint if flagged

    If you already had a flat config, spread the harness base in:

    import harness from './eslint/base.config.mjs'
export default [...harness, /* your overrides */]
  4. Start a new Claude Code session

    Hook registrations are snapshotted at session start — an already-open session will not see them. Run /hooks to confirm registration.

  5. Smoke the gates
    • Write a file named against convention → expect a PreToolUse deny
    • Edit a protected dir → expect a deny with the Open-Closed message
    • Finish a turn with failing checks → expect the Stop hook to block

Upgrade

Re-running the installer is the upgrade path — it is idempotent

scripts/ and .claude/hooks/ are overwritten with current versions. In .claude/settings.json, harness-owned hook entries are replaced, never duplicated; your own hooks and permissions are untouched. In harness.config.json, new keys are added and your tuned values always win (reviewers matched by name). The installer prints exactly what it added. Then start a new session.

One gate, three entry points

scripts/gate.sh is the single gate — Claude hooks (pre-commit + Stop), lefthook git pre-commit, and CI all run the same script, so they can never drift.

gate.sh --staged           # staged files (git pre-commit, Claude commit hook)
gate.sh --changed <base>   # committed + staged + unstaged vs base (Stop hook, CI)
gate.sh --all [--e2e]      # full sweep (CI main, on demand)

The Stop hook: three checks before the agent may finish

  1. gate.sh --changed — all deterministic checks.
  2. Peer-review proof — the activity log must show a code-reviewer subagent run newer than the last edit (harness.config.json → subagentReview).
  3. LLM review — each enabled CLI reviewer (e.g. codex) reviews the diff against clean-code.md; a report ending VERDICT: FAIL blocks when llmReview.mode is "block".

Fix rounds are capped per session by llmReview.maxRounds (default 2), so two models can never argue forever. Reports are saved under .harness/runs/ either way.

Severity model

SeverityMeaning
blockDeterministic failure — stops the commit / turn
block-newBlocks only regressions vs a committed baseline
reportAdvisory — surfaced, never blocks. New checks start here; promote after a week
offDisabled

Set per check in harness.config.json → checks. Only deterministic checks block — the one exception is the turn-end LLM review in "block" mode, and it is bounded by maxRounds.

Observability

  • Every gate run writes an artifact bundle under .harness/runs/<stamp>/: result.json, brief.md, per-check output in checks/.
  • Every tool call is appended to runs/<date>/events.jsonl by an async PostToolUse hook — it never blocks a tool call.
  • logging.enabled: false turns it all off; logging.retainDays (default 30) prunes old runs.

Escape hatches (all auditable)

  • // hoisted: <reason> — legitimate state lift
  • SKIP_TESTS_CHECK=1 — no-behaviour changes (renames, comments)
  • npx fallow dupes --save-baseline — accept justified duplication
  • node scripts/ratchet.mjs update — lock in improvements

Verify the install

# From the harness repo — its own test suite:
bash scripts/__tests__/run-logging.test.sh
bash scripts/__tests__/nested-config-gate.test.sh
bash scripts/__tests__/llm-review.test.sh
bash scripts/__tests__/check-filename.test.sh

# From the target project:
bash scripts/gate.sh --changed origin/main   # expect check output, not silence

Where the source lives

  • Rulebook: docs/clean-code.md — change a rule here first
  • Rule → layer → file map: README.md
  • Config: harness.config.json — severities, reviewers, logging, models
  • Gate + reviewers: scripts/gate.sh, scripts/llm-review.sh, scripts/review.sh, scripts/subagent-review-check.sh
  • Hooks: hooks/ → installed to .claude/hooks/
